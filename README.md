# AI-Checker — AI Content Detection POC

AI-Checker is a proof-of-concept web application that estimates the likelihood that a piece of text, an image, or a video was generated by AI. It is built on Next.js 16 (App Router) with TypeScript and Tailwind CSS, and it deliberately avoids running any detection model in-process — instead it calls out to third-party detection APIs and normalizes their responses into a single, consistent output shape. The core engineering problem this project solves is provider reliability: free-tier detection APIs rate-limit aggressively and occasionally go down, so every modality is backed by an ordered list of providers with an automatic fallback mechanism that retries the next provider transparently on failure. The result is a UI that degrades gracefully instead of surfacing a raw error the moment one vendor's quota is exhausted.

## Features

- **Multi-modal detection** — analyze text, images (JPG/PNG), audio (MP3/WAV/M4A/OGG/FLAC/WEBM), or video (MP4) from a single unified interface.
- **Unified output format** — every modality returns the same shape: a 0–100 percentage plus a verdict bucket (`Likely Human`, `Uncertain`, `Likely AI-generated`), never a bare yes/no.
- **Provider fallback chain** — each modality has an ordered list of detection providers; if the primary provider fails (rate limit, bad key, timeout, 5xx), the backend automatically retries the next one with no user-facing interruption.
- **Provider health reporting** — a `GET /api/health` endpoint reports which provider credentials are configured, designed for uptime monitors without burning vendor quota.
- **Rate limiting** — per-modality sliding-window caps (text 20/min, image 10/min, audio 6/min, video 4/min) return `429` with a `Retry-After` header.
- **Server-side file validation** — every upload is verified by magic bytes (the actual file signature), not just the client-declared MIME type, so renamed or spoofed payloads are rejected with a `400` before any provider call.
- **Video frame analysis** — samples up to 8 evenly-spaced frames from an uploaded video via FFmpeg, scores each one independently, and renders a per-frame timeline chart alongside the overall score.
- **Dark/Light theme** — respects the system color-scheme preference on first load and persists a manual override via a toggle in the header.
- **Animated result card** — an eased count-up percentage, a gradient progress bar (green → amber → red), and provider attribution, all driven by Framer Motion.
- **Client-side validation** — file type and size are checked in the browser before upload so rejected files never leave a wasted round trip to the server.
- **Mobile responsive** — the layout, tab switcher, and upload panels all adapt down to small viewports.
- **Skeleton loading states** — content-shaped placeholders during analysis instead of a generic spinner.
- **Toast notifications** — non-blocking success/error feedback via `react-hot-toast`, styled to match the active theme.

## Architecture Overview

```
┌─────────────┐     ┌──────────────────┐     ┌───────────────────────┐
│  Client UI  │ ──▶ │   API Routes      │ ──▶ │  detectWithFallback   │
│ (Check      │     │  /api/check/text  │     │  (lib/fallback.ts)    │
│  Panels)    │ ◀── │  /api/check/image │ ◀── │                       │
└─────────────┘     │  /api/check/audio │     └───────────┬───────────┘
                    │  /api/check/video │                 │
                     └──────────────────┘                 │
                                              ┌────────────┼────────────┐
                                              ▼            ▼            ▼
                                        ┌──────────┐ ┌──────────┐ ┌──────────┐
                                        │Provider 1│ │Provider 2│ │Provider 3│
                                        │(primary) │ │(fallback)│ │(fallback)│
                                        └──────────┘ └──────────┘ └──────────┘
```

Each modality's API route hands its request to `detectWithFallback`, a single generic orchestrator that has no knowledge of *which* vendor it's calling — it only knows it has an ordered array of objects implementing the shared `Provider` interface. It calls the first provider with an 8-second timeout; if that call throws (quota exceeded, invalid credentials, server error, timeout, or a response that fails schema validation), the orchestrator logs a warning and moves to the next provider in the array. The route only ever sees a successful `DetectionResult` or an exception that means every provider in the chain has been exhausted, which is the single condition that surfaces as a `503` to the client.

### Video Detection

Video detection reuses the image provider chain rather than maintaining a separate one. `lib/videoFrames.ts` extracts up to 8 evenly-spaced JPEG frames from the uploaded file with FFmpeg; each frame is then run independently through `detectWithFallback` using the same Sightengine → AI or Not chain used for still images. The per-frame percentages are averaged into an overall score, and the individual scores are returned alongside it for the frame timeline chart.

### Adding a New Provider

1. Implement the `Provider` interface from `lib/providers/types.ts` — a `name` string and a `detect(input: ProviderInput): Promise<DetectionResult>` method.
2. Inside `detect`, wrap all vendor-specific logic in a `try`/`catch` and throw `ProviderUnavailableError` for any failure that should trigger fallback (quota, bad key, malformed response, etc.).
3. Import the new provider into the relevant API route and add it to the array passed to `detectWithFallback`, in priority order.

No changes to the orchestrator, the API route's response shape, or the frontend are required — `detectWithFallback` only depends on the shared interface.

## API Endpoints

All detection endpoints run on the Node.js runtime (`export const runtime = "nodejs"`), which is required for the FFmpeg-based video route and kept consistent across the check routes for uniformity.

Every check endpoint is rate-limited per client IP — text 20/min, image 10/min, audio 6/min, video 4/min. Exceeding the cap returns `429` with a `Retry-After` header.

Upload endpoints are additionally validated server-side by magic bytes: the actual file signature must match the declared MIME type, otherwise the request is rejected with `400` before any provider is called.

### POST `/api/check/text`

Analyzes a block of text for AI-generation likelihood.

**Request body** (`application/json`):

```json
{ "text": "Your text to analyze here — at least 20 characters." }
```

**Success response** (`200`):

```json
{
  "percentage": 78,
  "verdict": "Likely AI-generated",
  "provider": "sapling"
}
```

**Error responses:**
- `400` — missing text, or fewer than 20 characters after trimming.
- `503` — every configured provider failed (rate limit, invalid credentials, timeout, or all keys unset).

**Example:**

```bash
curl -X POST http://localhost:3000/api/check/text \
  -H "Content-Type: application/json" \
  -d '{"text": "Your text to analyze here..."}'
```

### POST `/api/check/image`

Analyzes an uploaded JPG or PNG image (max 10MB).

**Request body** (`multipart/form-data`): a single field named `image`.

**Success response** (`200`):

```json
{
  "percentage": 12,
  "verdict": "Likely Human",
  "provider": "sightengine"
}
```

**Error responses:**
- `400` — no file provided, unsupported MIME type, file exceeds 10MB, or the file bytes don't match the declared type (magic-byte validation).
- `503` — every configured provider failed.

**Example:**

```bash
curl -X POST http://localhost:3000/api/check/image \
  -F "image=@/path/to/image.jpg"
```

### POST `/api/check/audio`

Analyzes an uploaded audio file (max 20MB).

**Request body** (`multipart/form-data`): a single field named `audio`.

**Success response** (`200`):

```json
{
  "percentage": 23,
  "verdict": "Likely Human",
  "provider": "sightengine"
}
```

**Error responses:**
- `400` — no file provided, unsupported MIME type, file exceeds 20MB, or the file bytes don't match the declared type (magic-byte validation).
- `429` — rate limit exceeded for this client (`Retry-After` header included).
- `503` — every configured provider failed.

**Example:**

```bash
curl -X POST http://localhost:3000/api/check/audio \
  -F "audio=@/path/to/audio.mp3"
```

### POST `/api/check/video`

Analyzes an uploaded MP4 video (max 20MB) by sampling and scoring individual frames.

**Request body** (`multipart/form-data`): a single field named `video`.

**Success response** (`200`):

```json
{
  "percentage": 45,
  "verdict": "Uncertain",
  "provider": "sightengine",
  "perFrame": [32, 41, 55, 48, 39, 52, 47, 44]
}
```

**Error responses:**
- `400` — no file provided, unsupported MIME type, file exceeds 20MB, the file bytes don't match the declared type (magic-byte validation), or the video could not be read/decoded by FFmpeg.
- `503` — every configured provider failed for the sampled frames.

**Example:**

```bash
curl -X POST http://localhost:3000/api/check/video \
  -F "video=@/path/to/video.mp4"
```

### GET `/api/health`

Operational status for uptime monitors and ops dashboards. It never calls a vendor API — it only reports which provider credentials are configured in the environment, so it is cheap to poll. Always returns `200`; `status` is `ok` when at least one provider is configured and `degraded` when none are.

**Success response** (`200`):

```json
{
  "status": "ok",
  "uptimeSeconds": 1204,
  "timestamp": "2026-09-16T06:30:00.000Z",
  "providers": [
    {
      "id": "sapling",
      "modality": "text",
      "role": "fallback",
      "envKeys": ["SAPLING_API_KEY"],
      "configured": true
    }
  ]
}
```

## Fallback Architecture

Every provider, regardless of modality or vendor, implements the same contract defined in `lib/providers/types.ts`:

```typescript
export interface DetectionResult {
  aiProbability: number;   // 0..1, normalized across all providers
  providerName: string;    // e.g. "sapling", "sightengine"
  raw?: unknown;           // original vendor response, for debugging only
}

export interface Provider {
  name: string;
  detect(input: ProviderInput): Promise<DetectionResult>;
}

export type ProviderInput =
  | { kind: "text"; text: string }
  | { kind: "image"; buffer: Buffer; mimeType: string }
  | { kind: "video-frame"; buffer: Buffer; mimeType: string };
```

`detectWithFallback(providers, input)` in `lib/fallback.ts` operates on this contract as follows:

1. Iterate over the `providers` array in the order supplied by the caller.
2. Call `provider.detect(input)`, racing it against an 8-second timeout.
3. On success, return the `DetectionResult` immediately — no remaining providers are called.
4. On failure, log a warning (`console.warn`) naming the provider and the reason, then continue to the next provider in the array.
5. If every provider in the array fails, throw an error aggregating all individual failure reasons; the calling API route catches this and responds with `503`.

**Failure conditions that trigger fallback:**
- `429` — rate limit or quota exceeded
- `401` / `403` — invalid or expired API key
- `5xx` — provider-side server error
- Timeout — no response within 8 seconds
- Schema mismatch — a response that doesn't match the expected shape

**Observability:** every fallback event is logged via `console.warn` in the shape `[fallback] {provider} failed: {reason}. Trying next provider...`, so a failover is visible in server logs even though it's invisible to the end user.

**How to test the fallback path:** set an intentionally invalid value for `SAPLING_API_KEY` in `.env.local`, restart the dev server, and submit a text check. The server log will show the Sapling call failing with an authentication error, followed immediately by an attempt against the next provider in the chain — demonstrating the exact behavior a real quota exhaustion would trigger in production.

## Usage Guide

### Text

1. Select the **Text** tab.
2. Paste or type at least 20 characters into the textarea. The live character count and a validation hint indicate when the minimum is met.
3. Click **Check Text**.
4. The result card displays the percentage, verdict, and which provider produced it (e.g. "via sapling").

### Image

1. Select the **Image** tab.
2. Drag and drop a JPG or PNG onto the upload area, or click it to open a file picker. Accepted formats and the file size are validated client-side before any upload begins.
3. **Limit:** 10MB max.
4. A thumbnail preview appears once a valid file is selected. Click **Check Image** to submit it.
5. The result card displays the percentage and verdict, identical in shape to the text result.

### Audio

1. Select the **Audio** tab.
2. Drag and drop an audio file onto the upload area, or click it to open a file picker. Accepted formats: MP3, WAV, M4A, OGG, FLAC, WEBM.
3. **Limit:** 20MB max.
4. Click **Check Audio**. The result card displays the percentage and verdict, identical in shape to the text and image results.

### Video

1. Select the **Video** tab.
2. Drag and drop an MP4 onto the upload area, or click it to open a file picker.
3. **Limit:** 20MB max, MP4 format only.
4. Click **Check Video**. This step takes noticeably longer than text or image checks, since the server extracts and scores multiple frames before responding.
5. The result card shows the overall percentage and verdict, plus a **per-frame timeline chart** so you can see which parts of the clip scored higher or lower.

> **Disclaimer:** every result card includes the caption *"This is a detection signal, not proof. Treat it as one input among several."* This is intentional and non-negotiable — AI detection is probabilistic, and no result from this tool (or any detector) should be treated as a certified verdict.

## Deployment Notes

- All three API routes require the Node.js runtime, not Edge — each route explicitly sets `export const runtime = "nodejs"`, since `fluent-ffmpeg` and Buffer-based file handling are unavailable on the Edge runtime.
- `fluent-ffmpeg` and `@ffmpeg-installer/ffmpeg` are listed under `serverExternalPackages` in `next.config.ts`. Both packages resolve their native binary paths via dynamic `require()` calls that bundlers can't statically analyze, so they're kept external and resolved by Node at runtime instead.
- Video processing has meaningfully longer execution times than text or image checks (frame extraction plus multiple sequential/parallel detection calls), which may exceed the execution time limits of some serverless platforms.
- For full, reliable video support, a long-running server environment (a VPS, Railway, Render, or similar) is recommended over a strictly serverless deployment target.
- Environment variables must be configured through the hosting platform's own dashboard or secrets manager — `.env.local` is a local-only file and is never deployed.

## Limitations & Scope

This is a proof-of-concept, and the following constraints are intentional rather than oversights:

- No user authentication or account management.
- No self-hosted or fine-tuned detection models — all scoring is delegated to third-party APIs.
- Video is restricted to MP4 format, capped at 20MB.
- Images are restricted to JPG/PNG, capped at 10MB.
- No persistent storage — results are not saved between sessions or requests.
- Detection accuracy is entirely dependent on the underlying third-party providers and their respective model quality.
- Free-tier API quotas are limited and will be exhausted under sustained or heavy usage.
- Not intended for production deployment without additional hardening (rate limiting, request auditing, provider quota monitoring, and a paid-tier provider strategy).
